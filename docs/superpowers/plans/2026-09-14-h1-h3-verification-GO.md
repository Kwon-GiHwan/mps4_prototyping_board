## 2. 공통 실험 조건

### 환경 통제
- X4와 동일한 FVP 바이너리·버전, MLEK·Vela·컴파일러 버전 사용.
- TA는 자동 선택에 맡기지 않고 전체 파라미터를 명시한다.
- 설정별 generated header와 적용 경로를 확인한다.
- 런타임 메모리 조건을 바꾸는 실험에서는 MAC별 Vela 산출물을 고정한다.
- MAC 구성을 비교할 때는 Vela의 시스템 가정도 공통으로 맞춘 별도 대조군을 만든다.
- 모델 입력·양자화·가중치·메모리 모드·arena/cache 조건을 기록한다.
- 각 조건을 독립 FVP 프로세스에서 3회 반복한다.

MAC별로 유효한 프로그램을 따로 사용한다. 하나의 MAC용 산출물을 다른 MAC 설정에서 강제로 실행해 프로그램을 통일하지 않는다. Vela는 대상 NPU에 맞는 command stream을 생성하는 단계이므로, 대상 변경과 런타임 설정 변경을 구분한다.

### 공통 수집 항목

| 분류 | 수집 내용 |
|---|---|
| 실행 비용 | TOTAL, ACTIVE, 파생 IDLE |
| 메모리 | 수집 가능한 SRAM/EXT read/write beats |
| 프로그램 구조 | 연산·launch·block·tile 정보, 메모리 배치, encoded weight 크기 |
| 재현성 | 모델·Vela 산출물·AXF 해시, 입력 식별 정보 |
| 원시 증거 | 전체 UART, 오류·overflow 메시지, 실제 실행 명령 |

검증 구현 때문에 바이너리가 달라지는 경우에는 검증용 clean 대조군을 같은 구현으로 만들고 계측 영향을 평가한다. 종료된 S4의 미검증 stall 값을 이번 결과의 근거로 재사용하지 않는다.

## 3. 실험 H1 — 외부 지연 민감도와 직렬화 가설 검증

### 연구 질문
RNNoise의 지연 민감도는 읽기·쓰기 중 어디에서 발생하는가? 요청 동시성을 늘리면 민감도가 줄어드는가? MAC별 민감도가 실제로 유사한가?

### H1-A. 읽기·쓰기 지연을 분리한다
RNNoise U85 256·512·1024·2048에서 다음을 수행한다.

| 실험 | 변경 변수 | 고정 변수 |
|---|---|---|
| 읽기 지연 sweep | EXT_RLATENCY = 0 / 125 / 250 / 500 / 1000 | EXT_WLATENCY = 250, 나머지 TA 동일 |
| 쓰기 지연 sweep | EXT_WLATENCY = 0 / 125 / 250 / 500 | EXT_RLATENCY = 500, 나머지 TA 동일 |
| 두 지연 제거 | 읽기·쓰기 모두 0 | 나머지 TA 동일 |

읽기·쓰기 지연은 TA의 별도 파라미터이므로, 기존의 읽기 L·쓰기 L/2 결합 실험에서 두 효과를 분리하는 것이 목적이다.

### H1-B. 요청 동시성을 조작한다
RNNoise U85 256·512를 우선 대상으로 다음을 수행한다.
- EXT_MAXR = 1 / 4 / 16 / 64
- 읽기 지연: 250 / 1000
- 쓰기 지연·BWCAP·pulse·SRAM 설정 고정.
- MAXRW나 NPU 자체 요청 제한이 실험 범위를 잘라내지 않는지 확인.

NPU의 실제 outstanding 제한은 TA 설정뿐 아니라 구성 핀·레지스터 제한에도 영향을 받으므로, 설정한 값과 실제 적용 가능한 값을 구분한다.

### 이 실험으로 구분할 것

| 결과 | 의미 |
|---|---|
| 읽기 지연에서 주로 변화 | 읽기 경로의 지연 민감성 지지 |
| 쓰기 지연에서도 변화 | 기존 기울기를 읽기 횟수로 해석할 수 없음 |
| MAXR 증가로 지연 민감도 감소 | 동시 요청 제한·전송 겹침의 역할 지지 |
| MAXR을 바꿔도 민감도 유지 | 직렬 의존성 또는 다른 제한을 추가 조사 |
| MAC별 기울기가 다름 | "접근 횟수는 MAC과 무관"이라는 설명 수정 |

정적 DMA 명령 수뿐 아니라 실제 block별 전송 구조와 의존 관계를 함께 조사한다. U85의 IFM·OFM·weight 전송은 내부 block 처리에서도 발생하므로, 명령 개수를 실제 transaction 횟수와 동일시하지 않는다.

### H1-C. 새로운 조건에서 예측을 검증한다
- 실측 C(0)와 회귀 절편을 분리한다.
- 모든 MAC에 공통인 지연 구간으로 기울기를 비교한다.
- 기존 구간으로 만든 모델이 미사용 지연값 375·750의 사이클을 예측하는지 새로 측정한다.
- 예측식과 허용 오차 기준은 해당 검증값을 보기 전에 고정한다.
- KWS·AD의 U85 256·512에서도 읽기 지연 0 / 250 / 500 / 1000을 측정해 RNNoise 특성의 일반화 여부를 확인한다.

완료 목표: "직선이 잘 맞는다"를 넘어, 읽기·쓰기·요청 동시성 중 어떤 요소가 민감도를 만드는지 실험적으로 구분한다.

## 4. 실험 H2 — Wav2Letter 잔여 비용의 원인 검증

### 연구 질문
지연을 제거해도 남는 Wav2Letter의 비용은 외부 대역폭 제한 때문인가? 그중 가중치 전송의 기여는 무엇인가?

### H2-A. 외부 대역폭 × 지연 실험
Wav2Letter U85 512를 주 대상으로, 256을 확인 대상으로 수행한다.

| 변수 | 수준 |
|---|---|
| EXT BWCAP | 기본값의 0.5배 / 1배 / 2배 / 0 |
| EXT 지연 | 기본 읽기·쓰기 지연 / 읽기·쓰기 모두 0 |
| 고정 | Vela 산출물, SRAM 조건, 요청 제한, pulse, 입력 |

BWCAP=0은 대역폭 quota를 해제하는 설정이지 TA 전체 비활성화가 아니다. pulse의 차단 구간은 별도로 유지·기록한다.

측정할 것은 사이클 감소뿐 아니라 실제 EXT 전송량과 달성 전송률이다. 설정상 BWCAP을 높여도 물리 인터페이스나 다른 제한 때문에 실효 대역폭이 높아지지 않았다면, 그것을 "대역폭 영향 없음"의 근거로 사용하지 않는다.

### H2-B. 가중치 전송을 직접 구분하는 대조군
외부 대역폭의 효과가 확인되면 다음 단계로 진행한다.
- Wav2Letter에서 대표적인 큰 가중치 연산을 추출한다.
- 해당 레이어의 가중치를 SRAM에 두는 구성과 EXT에 두는 구성을 만든다.
- 가능한 한 연산·입출력·가중치 값·스케줄을 유지하고 배치만 변경한다.
- 배치 변경으로 command stream이나 스케줄이 바뀌면 그 차이를 별도 기록한다.
- 전체 모델이 SRAM에 들어가지 않는다면 대표 레이어 단위로 실험한다.

외부 경로에는 가중치 외에 IFM·OFM·중간 데이터도 이동하므로, EXT 전체 트래픽 감소만으로 가중치 기여를 확정하지 않는다.

### 결과에 따른 다음 분기

| 결과 | 후속 판단·실험 |
|---|---|
| BWCAP 완화로 사이클 감소 | 외부 대역폭 제약의 개입 효과 확정 |
| 가중치 SRAM 배치로 트래픽·사이클 감소 | 대표 레이어의 가중치 전송 부담 확인 |
| BWCAP 실효 완화에도 변화 없음 | 외부 대역폭 하한 가설을 반증하고 SRAM·계산·디코더 쪽을 조사 |
| 지연·대역폭을 함께 완화해야 개선 | 두 제약의 상호작용으로 정리 |

완료 목표: "지연을 없애도 남는다"에서 끝내지 않고, 잔여 비용이 무엇에 반응하는지 확인한다.

## 5. 실험 H3 — 공간 형상과 MAC/block 매핑을 분리한다

### 연구 질문
작은 공간 크기 자체가 문제인가, H·W 방향의 block 정렬이 문제인가, 아니면 메모리 이동·스케줄 변경의 효과인가?

### H3-A. 연산량을 유지한 공간 형상 실험
먼저 단일 1×1 Conv 모델을 만들어 다음처럼 비교한다.

| 고정 | 변경 |
|---|---|
| INT8, 입력·출력 채널 수, 가중치 값, H×W=36 | 1×36, 2×18, 3×12, 4×9, 6×6 및 전치 형상 |
| 커널·stride·양자화 조건 | H와 W의 배치 |
| 공통 Vela 시스템 가정·TA 조건 | U85 256 / 512 |

이렇게 하면 공간 원소 수·명목 연산량·가중치 크기를 유지하면서 형상의 효과를 볼 수 있다.

수집 항목: H, W, C · 실제 ublock / block / tile 구성 · 각 차원의 나머지·padding · TOTAL cycles · SRAM / EXT traffic · encoded weights · 256→512 사이클 비

H×W / MAC 같은 비율을 이용률로 사용하지 않고, 실제로 생성된 block 매핑과 실행 변화를 연결한다.

### H3-B. 연산 종류와 공간 크기의 효과를 분리한다
- 같은 공간 형상 집합을 3×3 Conv와 3×3 DWConv에도 적용한다.
- 각 연산 유형 내부에서 채널·커널·stride·padding 조건을 고정한다.
- padding이나 경계 처리로 실제 계산량·입력 전송량이 달라진 부분은 따로 기록한다.
- 공간 면적을 36 → 64 → 256으로 확장해 형상 효과와 전체 공간 크기 효과를 분리한다.
- 기본 TA 조건과 TA 제약을 완화한 조건에서 같은 검사를 수행한다.

### 판정할 내용

| 관측 | 판단 |
|---|---|
| 같은 H×W에서도 형상에 따라 확장 이득이 달라짐 | 공간 면적만의 설명 반증, 방향별 매핑 효과 지지 |
| block 경계에서 비용이 반복적으로 달라짐 | geometry 연관성을 넘어 통제된 형상 개입 근거 확보 |
| 메모리 조건 완화 후 형상 차이가 사라짐 | geometry와 memory-service의 상호작용 조사 |
| 연산 유형별 결과가 다름 | "연산 종류와 무관"이라는 부분 반증 |
| 공간 확장 후에도 개선이 일관되지 않음 | 단순 작은-feature-map 가설 수정 |

U85 1024→2048은 SRAM 포트 수도 바뀌므로, 첫 geometry 실험은 포트 수가 같은 256/512에서 수행하고 이후 확장한다.

완료 목표: 실제 모델의 상관관계만으로 판단하지 않고, 형상·면적·연산 종류를 직접 바꿔 원인을 구분한다.

## 6. 기존 SRAM 가설도 별도 개입으로 확인한다

평균 이용률만으로 기각했던 부분을 해결하기 위해 KWS·AD의 U55/U65 대표 구성에서 SRAM BWCAP 변주를 추가한다.

| 항목 | 설정 |
|---|---|
| 변경 | SRAM BWCAP: 기본값의 0.5배 / 1배 / 2배 / 0 |
| 고정 | SRAM 지연, EXT 전체 설정, 프로그램·입력 |
| 수집 | 사이클, SRAM 전송량, 달성 전송률 |
| 목적 | 기본 구성에서 TA의 SRAM 대역폭 제한이 실제로 성능을 제한하는지 확인 |

cap을 낮춰 느려졌다는 결과와 기본 cap을 완화해 빨라졌다는 결과를 구분한다. 기본 cap이 이미 인터페이스의 실효 상한보다 높다면, 이 실험은 TA cap의 영향만 검사한 것으로 기록하고 물리 SRAM 대역폭까지 배제하지 않는다.

## 7. 실행·판정 원칙

### 중단 기준
- 프로그램 실행 실패, 출력 불일치, overflow, 의도하지 않은 설정 변경은 해당 실험의 중단 사유.
- 가설과 반대되는 결과는 중단 사유가 아니라 정상적인 연구 결과.
- 파일 해시가 설정 변경 때문에 의도대로 달라진 경우와 의도하지 않은 변경을 구분한다.
- 반복 오차·계측 영향을 확인하는 예비 실험과 최종 가설 검증 표본을 분리한다.
- 효과 크기·모델 예측 오차의 판정 기준은 최종 검증 전에 고정한다. 결과를 본 뒤 맞추지 않는다.

### 최종 산출물
- 새 실험 계획서
- 실제 실행 매트릭스와 설정 manifest
- 원시 UART 및 입력·출력 검증 자료
- 조건별 측정 CSV
- 지연·대역폭·형상 변화 그래프
- 가설별 예측과 관측의 대조표
- 기존 7개 요인의 갱신 판정
