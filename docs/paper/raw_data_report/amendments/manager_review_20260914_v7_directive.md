## §1 전달받은 전문

**제안한 표 그대로 v7로 바꾸는 것은 보류하는 게 맞습니다.** 새 가설을 만드는 방향은 좋지만, 현재 안에는 **H1′의 회귀계수 해석 오류, H2′의 잔여 비용에 대한 성급한 귀속, H3′의 공간 크기 계산 오류**가 있습니다.

다만 자료 개편 자체를 멈출 필요는 없습니다. **20–22장은 검증된 결과로 정리하고, 25장에 수정한 세 가설을 '후속 검증 가설'로 분리하는 방식**을 권합니다.

### 1. H1′ — 선형 근사는 가능하지만, 현재 식과 물리적 해석은 수정해야 합니다

#### ① 제시한 '하한'과 기울기는 서로 다른 방식으로 구한 값입니다

앞서 공유한 X4 조건별 사이클에 동일 가중치를 주고 다음 식을 재적합했습니다.

C_M(L) ≈ a_M + k_M L

| RNNoise U85 | 실제 측정한 C_M(0) | 회귀 절편 a_M | 회귀 기울기 k_M |
| --- | ---: | ---: | ---: |
| 256 MAC | 21,086 | **15,461** | 98.20 |
| 512 MAC | 16,086 | **11,011** | 92.10 |
| 1024 MAC | 11,086 | **8,686** | 84.91 |
| 2048 MAC | 11,086 | **9,086** | 92.00 |

제안한 `k = 98 / 92 / 85 / 92`는 **절편을 자유롭게 적합한 회귀 기울기**와 일치합니다. 그런데 '하한'에는 회귀 절편이 아니라 **실측 C(0)**를 넣었습니다.

따라서 현재의 `사이클 = 실측 C(0) + 위에서 구한 k × L`은 **실제로 적합한 회귀식이 아닙니다.**

두 방법 중 하나로 고쳐야 합니다.

| 방법 | 표현 |
| --- | --- |
| 선형 회귀로 요약 | 회귀 절편 a_M와 기울기 k_M를 함께 사용 |
| 실측 0-지연 값을 기준으로 비교 | C_M(L) = C_M(0) + ΔC_M(L)로 표시. 선형성을 강제하지 않음 |

**보고자료에는 두 번째가 더 안전합니다.** 회귀식은 곡선을 요약하는 보조 모델로 두면 됩니다.

또한 256 MAC의 구간별 기울기는 **40 → 80 → 104 → 108**입니다. 전체적으로 선형 근사가 잘 맞더라도, **모든 지연 구간에서 동일한 대기 횟수가 작용한다고 바로 해석할 수는 없습니다.**

#### ② 기울기 k는 '직렬 외부 왕복 횟수'로 확정할 수 없습니다

현재 X4는 읽기 지연을 L, 쓰기 지연을 L/2로 **함께 변경**했습니다. 따라서 k는 우선 **그 설정 묶음에 대한 실행 사이클의 민감도**입니다. TA의 읽기·쓰기 지연도 각각 정의된 설정값이지, 측정된 외부 메모리 왕복 횟수가 아닙니다.

겹침이 전혀 없는 단순 직렬 모델에서도 기울기는 k = N_read + ½ N_write 처럼 될 수 있습니다.

실제 NPU에는 outstanding transaction, buffering, 연산·전송 겹침이 있으므로 더 복잡합니다. Arm 문서도 DMA의 동시 요청 제한과 가중치 읽기 버퍼를 통한 지연 은닉을 설명합니다. (Arm Ethos-U85 NPU Technical Overview)

따라서 현재 이름은 다음이 정확합니다.

> **k: 평가 구간에서의 실효 지연 민감도**

`직렬 접근 횟수`는 **그 민감도를 설명하기 위한 추가 가설**로 남겨야 합니다.

명령 스트림에서 DMA 명령 개수를 세는 것도 보조 근거는 되지만, **명령 하나가 실제 AXI transaction 하나를 뜻하지는 않습니다.** U85의 IFM·OFM·weight 전송은 내부 블록 단위 실행에서도 발생합니다.

#### ③ "MAC과 무관", "MAC은 하한만 줄인다"도 아직 성립하지 않습니다

기울기는 실제로 85–98 사이에서 달라지고, MAC별로 적합한 지연 범위도 다릅니다. 특히 512는 2,000까지, 나머지는 1,000까지 포함합니다. **MAC 간 기울기를 비교하려면 먼저 공통 지연 구간으로 맞춰야 합니다.**

현재 가능한 표현은: **RNNoise에서는 MAC 구성 변경 후에도 외부 지연 설정에 대한 민감도가 유지된다.** 입니다. **민감도가 MAC에 독립적이라는 결론은 아닙니다.**

"기본 지연에서 지연 항이 항상 하한보다 크다"는 설명도 실제 값과 맞지 않습니다. 256 MAC에서는 C(250) − C(0) = 36,086 − 21,086 = 15,000 으로, **지연 제거에 따른 감소분 15,000이 잔여 사이클 21,086보다 작습니다.** 이 감소분도 개입의 순효과이지 직접 측정한 stall 시간은 아닙니다.

또 `7×500=3,500`은 실제 두 번째 역전 **5,000 cycles의 70%**입니다. 이를 "크기가 맞으므로 원인이 설명됐다"고 쓰면 안 됩니다. 같은 데이터를 적합해 얻은 계수로 같은 데이터를 설명하는 것은 독립적인 메커니즘 검증도 아닙니다.

#### H1′ 수정안

> **RNNoise의 실행 비용은 외부 메모리 지연 설정에 민감하며, 그 민감도와 지연 0에서의 잔여 비용은 MAC 구성별로 다르다. 지연 민감도가 직렬화된 메모리 의존성과 어떤 관계를 갖는지는 후속 검증 대상이다.**

현재는 **RNNoise에서 확인한 결과**이므로, 제목부터 모든 '소형 모델'로 일반화하지 않는 것이 좋습니다.

### 2. H2′ — "지연 0에서도 비용이 남는다"는 맞지만, "가중치 전송이 하한을 정한다"는 미검증입니다

Wav2Letter에서 지연 0으로 바꿔도 기존 사이클의 약 92–99%가 남는다는 것은 중요한 관측입니다.

하지만 그것이 직접 뜻하는 것은: **기본 구성에서 TA EXT 읽기·쓰기 지연을 제거하는 것만으로는 대부분의 실행 비용이 줄어들지 않는다.** 입니다.

**지연 0은 메모리 접근 비용 전체를 0으로 만드는 설정이 아닙니다.** BWCAP, pulse, 요청 수 제한 등은 별도로 남습니다.

잔여 비용의 후보에는 계산, 가중치 해제, 메모리 전송, 내부 버퍼·파이프라인 처리 등이 있습니다. NPU의 외부 접근도 가중치만이 아니라 IFM·OFM·중간 데이터와 관련될 수 있습니다.

따라서 다음 연결은 아직 성립하지 않습니다.

```text
EXT 지연을 제거해도 비용이 많이 남음
                  ↓
그 비용은 가중치 전송량이 결정함
```

#### 제안한 BWCAP 실험은 유효하지만, 입증하는 범위가 다릅니다

Wav2Letter U85-512에서 BWCAP을 완화했을 때 사이클이 10% 이상 감소한다면: **해당 구성에서 EXT bandwidth cap의 제한 효과가 관측됐다.** 고 말할 수 있습니다.

그러나 이것만으로 **가중치 전송이 원인**이라고 특정할 수는 없습니다. 외부 트래픽 중 가중치가 차지하는 부분과 재사용·반복 전송을 구분해야 합니다. 가중치는 압축·재배열되어 전송되므로 원본 weight 크기가 곧 실행 중 전송 바이트 수인 것도 아닙니다.

U55/RNNoise에서 BWCAP 효과를 관측한 사실도 **U85/Wav2Letter의 가중치 병목을 대신 검증하지는 않습니다.**

#### H2′ 수정안

> **Wav2Letter의 지연 0 조건에서 남는 실행 비용에는 외부 메모리 전송 대역폭 제약이 기여할 수 있다. BWCAP 개입으로 이를 검증하되, 가중치 전송의 기여는 별도로 확인한다.**

즉 **외부 대역폭 제약 가설**과 **가중치 streaming 귀속 가설**을 나누는 것이 맞습니다.

### 3. H3′ — 현재 제안에서 가장 먼저 고쳐야 하는 부분입니다

#### ① 제시한 ublock의 공간 면적은 커지지 않습니다

| 구성 | ublock | 공간 면적 H×W | 채널 폭 |
| --- | --- | ---: | ---: |
| 256 MAC | `[1,4,8]` | **4** | 8 |
| 512 MAC | `[2,2,16]` | **4** | 16 |

즉 변화는: **높이 1→2, 너비 4→2, 채널 폭 8→16** 입니다. **공간 면적이 증가한 것이 아니라 공간 형상이 바뀌고 채널 폭이 증가한 것**입니다.

실제 256 스케줄에서 `[1,2,16]`을 사용하는 연산도 있다면 그 연산은 별도로 비교해야 합니다. 하나의 ublock 전환을 모든 연산에 적용해서는 안 됩니다.

#### ② `H×W`만으로 형상 불일치를 판정할 수 없습니다

H=1, W=36 → H×W=36 / H=6, W=6 → H×W=36. 두 출력은 공간 면적이 같지만 height=2인 블록에 매핑할 때 경계·패딩 조건은 다릅니다. 따라서 `H×W ≤ 블록 공간 크기이면 이득 없음` 이라는 한 개의 임계값은 **형상과 방향을 잃어버린 검사**입니다.

더구나 제시한 regression 그룹의 공간 크기 중앙값은 **36**인데, 위 ublock의 공간 면적은 **4**입니다. **중앙값 36 vs 256이라는 차이가 '공간 크기 ≤4'라는 임계 조건을 뒷받침하는 것은 아닙니다.**

#### ③ 작은 공간 크기와 ublock을 '같은 원인의 두 얼굴'로 합치기는 이릅니다

현재 직접 관측한 것은: **일부 분석 범위에서 실행 비용이 증가한 연산의 공간 크기가 더 작았다.** 입니다.

다음은 아직 가설입니다: **그 이유는 출력 형상이 변경된 ublock에 맞지 않기 때문이다.**

또 연산 종류의 비율이 비슷하다는 사실만으로 **연산 종류와 무관하다**고 결론 내릴 수는 없습니다. 연산 종류별·모델별로도 같은 관계가 유지되는지와, 해당 실행 비교의 TA 조건이 통제되었는지를 구분해야 합니다.

#### H3′ 수정안

> **작은 공간 크기와 출력 형상의 블록 매핑 특성이 특정 MAC 전이의 실행 비용 변화와 연관될 수 있다. 이 관계가 연산 종류·채널·메모리 조건을 고려한 뒤에도 유지되는지 검증한다.**

후속 검사는 단순 `H×W` 임계값보다 **H·W·C별 경계 조건, 실제 ublock/block 구성, tile 수**를 기준으로 만드는 편이 낫습니다. 이 지표도 실측 PE 이용률과는 구분해야 합니다.

입력 해상도를 키우는 실험은 보조적으로 유용하지만, **연산량·activation 크기·DMA·컴파일러 배치까지 함께 바뀌므로 geometry 하나만의 검증은 아닙니다.**

### 4. 20장 요인표는 기존 번호를 유지하고, 판정을 정확히 고치는 것이 좋습니다

새 가설이 나왔다고 기존의 미확정 항목을 삭제하거나 검증된 결과로 교체할 필요는 없습니다.

외부 대역폭은 SRAM과 섞지 말고 표 아래에 별도로 표시하면 됩니다.

> **추가 개입 결과: U55/RNNoise에서 EXT bandwidth cap 완화 효과와 지연 설정과의 상호작용 확인.**

특히 **6번을 H1′의 '하한'에 흡수하는 것은 승인하지 않습니다.** C(0)에는 계산·전송·내부 처리 비용 등이 남아 있을 수 있으므로, 아직 '연산 외 고정 비용'으로 분류할 수 없습니다.
