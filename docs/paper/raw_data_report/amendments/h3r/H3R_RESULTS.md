## 1. 원래의 통제 문제

H13 §6b′가 기록한 H3의 두 가지 통제 한계가 이 실험의 출발점이다.

1. **형상마다 양자화가 달랐다.** `h13/gen_h3_models.py`는 형상별 seed(`1000 + H·1000 + W`)의 대표 데이터로 각 모델을
   따로 INT8 변환했다. 그 결과 같은 연산 종류라도 형상마다 입력 zero-point와 출력 scale·zero-point가 다르고
   (1×1 Conv 기준 1×36: 입력 zp −1 · 출력 scale 0.062048 / zp 2, 36×1: 입력 zp 0 · 출력 scale 0.059312 / zp 13,
   6×6: 입력 zp −1 · 출력 scale 0.060005 / zp 7), bias와 재양자화 승수도 다르다. `h3_manifest.json`의
   `weights_sha256`은 **양자화 전 float 가중치**의 해시이므로 최종 INT8 버퍼가 같다는 근거가 되지 못한다.
   따라서 "형상만 바꿨다"는 진술은 float 수준에서만 성립했다.
2. **완화(relaxed) 조건도 MAC 간 동일 조건이 아니었다.** 지연과 BWCAP은 같게 맞췄지만 EXT_MAXR의 **적용값**이
   256에서 24, 512에서 무제한(요청 64가 드라이버의 6비트 마스크로 0)이고 EXT_MAXW도 12 대 32로 달랐다.
   그래서 "완화에서도 DW의 형상 차이가 남으니 매핑 자체가 원인"이라는 설명은 성립하지 않았다.

H3-R은 이 두 가지를 각각 제거하고, 제거한 뒤에 무엇이 남고 무엇이 사라지는지를 본다.

## 2. 실제로 고정한 것과 바꾼 것

### 2.1 고정한 것 — 최종 INT8의 비형상 요소 (G1′)

연산 종류별 기준 모델은 H3의 6×6 INT8 모델을 그대로 재사용했다(재calibration 없음).

| 연산 | 기준 모델 | sha256 |
|---|---|---|
| 1×1 Conv | `h3_conv1x1_6x6_c128` | `e0a1edbf…da71b` |
| 3×3 Conv (SAME) | `h3_conv3x3_6x6_c128` | `d9fb69c8…a4345` |
| 3×3 DWConv (SAME) | `h3_dw3x3_6x6_c128` | `c906b2de…bef7a` |

`gen_h3r_models.py`가 각 기준 모델의 flatbuffer를 읽어 **IFM(텐서 0)과 OFM(텐서 3)의 `shape` 필드만**
`[1,H,W,128]`로 바꿔 재직렬화했다. 면적 36의 9형상(1×36, 2×18, 3×12, 4×9, 6×6, 9×4, 12×3, 18×2, 36×1) × 3종 = 27모델.

`check_g1prime.py`가 기준 대 파생을 필드 단위로 비교해 **27/27 통과**했다. 연산 종류별로 9형상의 최종 INT8
가중치 버퍼 해시는 하나뿐이고(1×1 `ffe8eccb…`, 3×3 `756c05ce…`, DW `3c2412d3…`), bias 버퍼 해시도 하나뿐이며
(`9dafe9db…`, `e4bcdede…`, `cc772986…`) 양자화 레코드도 하나뿐이다. 검사 항목과 규칙 id는 다음과 같다.

| 확인 | 규칙 id | 결과 |
|---|---|---|
| 최종 INT8 가중치 버퍼 sha256 | `RULE_G1P_WEIGHTS` | 연산 종류별로 9형상 모두 동일 |
| bias 버퍼 sha256 | `RULE_G1P_BIAS` | 동일 |
| IFM·가중치·bias·OFM 양자화 레코드(scale 전부·zero-point 전부·quantized_dimension) | `RULE_G1P_QUANT` | 동일 |
| opcode·버전·builtin options(padding/stride/dilation/activation/depth_multiplier)·입출력 연결 | `RULE_G1P_OPERATOR` | 동일 |
| 텐서 수·dtype·이름·버퍼·비-IFM/OFM 텐서 shape·채널 수·메타데이터 버퍼 | `RULE_G1P_STRUCTURE` | 동일 |
| IFM/OFM shape = `[1,H,W,128]`, shape_signature 없음 | `RULE_G1P_SHAPE` | 의도한 형상과 일치 |

각 규칙은 자기 돌연변이 fixture를 가진다(`check_g1prime.py` 의 `G1PrimeRules`, 9 테스트). 6×6 파생본은 기준 모델과
**바이트 동일**했고(자기 검사), TF 인터프리터 실행에서도 기준 모델과 출력이 동일했다.

파일 전체 sha256은 형상이 다르므로 모델마다 다르다(재직렬화). 이는 정상이며 `derived_models.json`에 기록돼 있다.

### 2.2 기능 확인

`func_check.py`가 27모델을 TF 인터프리터로 로드·실행했다. 연산 종류별 공통 입력 벡터는
`numpy.random.default_rng(20260915)`의 int8 4,608바이트(sha256 기록)이며 각 H×W로 reshape해 넣었다.
27/27 로드·실행 성공, 출력 shape 전부 `[1,H,W,128]`. 서로 다른 형상의 출력이 같아야 한다는 조건은 두지 않았다.
인터프리터 성공은 NPU 출력 검증을 대신하지 않으며, NPU 출력 동일성은 서버 검증 빌드의 출력 게이트로 따로 확인했다(§3).

**3×3 SAME-padding의 형상 의존성(해석 시 명시).** 면적이 같아도 경계·패딩 비중은 형상마다 다르다.
`model_manifest.csv`의 `padding_note` 열에 형상별로 기록했다. 36칸 중 패딩에 닿는 OFM 위치의 비율은
6×6에서 20칸(56%)으로 가장 낮고, 4×9·9×4는 22칸(61%), 3×12·12×3은 26칸(72%), 1×36·2×18·18×2·36×1은
36칸 전부(100%)다. 게다가 1×36과 36×1에서는 커널의 두 행(또는 두 열)이 패딩만 읽는다. 따라서 3×3 결과의
형상 차이는 이 패딩 비중 변화를 **포함한** 효과이며, 특정 내부 유닛의 효과로 자동 귀속하지 않는다.

### 2.3 바꾼 것 — TA 조건 세 가지

모든 빌드에 SRAM·EXT 16개 값을 `-D`로 전부 넘겼고, 어떤 항목도 MLEK의 MAC별 자동 기본값에 맡기지 않았다.

| 값 | base 256 (low) | base 512 (mid) | equalized (두 MAC 동일) | bridge_legacy_relaxed 256 | bridge_legacy_relaxed 512 |
|---|---|---|---|---|---|
| SRAM_MAXR / MAXW / MAXRW | 8 / 8 / 0 | 8 / 8 / 0 | 8 / 8 / 0 | 8 / 8 / 0 | 8 / 8 / 0 |
| SRAM_RLATENCY / WLATENCY | 16 / 16 | 32 / 32 | 0 / 0 | 0 / 0 | 0 / 0 |
| SRAM_PULSE_ON / OFF / BWCAP | 3999 / 1 / 4000 | 3999 / 1 / 4000 | 3999 / 1 / 4000 | 3999 / 1 / 4000 | 3999 / 1 / 4000 |
| EXT_MAXR (요청 → 적용) | 24 → 24 | 64 → **0** | 0 → 0 | 24 → 24 | 64 → **0** |
| EXT_MAXW / MAXRW | 12 / 0 | 32 / 0 | 0 / 0 | 12 / 0 | 32 / 0 |
| EXT_RLATENCY / WLATENCY | 250 / 125 | 500 / 250 | 0 / 0 | 0 / 0 | 0 / 0 |
| EXT_PULSE_ON / OFF | 4000 / 1000 | 4000 / 1000 | 4000 / 1000 | 4000 / 1000 | 4000 / 1000 |
| EXT_BWCAP | 2344 | 3750 | 0 | 0 | 0 |

- **base**는 H3와 같은 MAC별 MLEK 프로파일이다. Vela system_config도 H3와 같이 256 = `Ethos_U85_SYS_DRAM_Low`,
  512 = `Ethos_U85_SYS_DRAM_Mid_512`로 유지했다. 따라서 이 실험을 "물리 MAC 배열 크기만 다른 실험"이라고 부르지 않는다.
- **equalized**는 GO §3.1의 7개 0(EXT R/W 지연, EXT_BWCAP, SRAM R/W 지연, EXT_MAXR, EXT_MAXW)에 더해 나머지 9값도
  두 MAC에 같은 값으로 명시했다. `EXT_PULSE_OFF`는 완주가 확인된 1000을 유지했다(H13 A7: 0은 FVP가 완주하지 못한다).
  "무제한"은 해당 TA 요청 제한 또는 bandwidth quota가 해제됐다는 뜻으로만 쓴다.
- **bridge_legacy_relaxed**는 기존 H3 relaxed의 정의를 그대로 재사용한 DW 전용 연결 대조군이다(프로파일 위에
  `EXT_RLATENCY/EXT_WLATENCY/EXT_BWCAP/SRAM_RLATENCY/SRAM_WLATENCY = 0`만 덮음). 기억으로 재구성하지 않고
  `make_cells.py`가 `h13/results.jsonl`의 DW relaxed arm `defines`와 **바이트 동일**함을 단언한 뒤 셀을 만든다.
  이 대조군이 분리하는 것은 다음 두 단계다.

  ```
  기존 H3 DW        : 형상별 양자화 + 기존 relaxed
  H3-R DW 연결 대조 : 공통 기준 양자화 + 기존 relaxed     <- 양자화만 바뀜
  H3-R DW 주 실험   : 공통 기준 양자화 + equalized        <- 거기서 MAXR/MAXW까지 동일화
  ```

**equalized 실효 동일성.** 생성 헤더는 캠페인이 설정하는 16값 외에 `PERFCTRL`·`PERFCNT`·`MODE`·`HISTBIN`·`HISTCNT`(양측)도
담는다. 판정기는 드라이버 마스크를 적용한 뒤 **26개 필드 전부**를 두 MAC 사이에서 비교했고 27모델 모두 일치했다.
따라서 equalized에서 "관리하지 않은 필드가 MAC마다 달랐다"는 가능성은 남지 않는다.

**첫 셀 qualification과 anchor 비교.** 대표 셀 `h3r_conv1x1_6x6_c128` × 256 base를 3회 + 검증 빌드로 먼저 돌렸다.
기존 H3의 같은 조건(`h3_conv1x1_6x6_c128` 256 base)과 비교하면 TOTAL 6,068 · ACTIVE 5,909로 **같고**, Vela 산출물 sha
`29c52c81…`와 출력 덤프 sha `9946a899…`도 **같다**(모델 바이트가 6×6에서 기준과 동일하므로 산출물까지 같다).
이는 게이트가 아니라 관측으로 기록한 것이다.

실행 순서상 qualification은 두 번 돌렸다. 첫 실행은 하니스가 CMakeCache 판독값을 레코드에 기록하지 않아 실효 설정
열이 비어 있었다(측정값 자체는 최종 실행과 동일). 하니스를 고쳐 다시 돌렸고, 첫 실행은 `results_qual_precachefix.jsonl`로
보존하되 결과에는 쓰지 않는다. 같은 점검에서 판정기도 고쳤다 — **읽지 못한 실효 설정을 통과로 처리하던 분기**를 거부로
바꾸고(`RULE_H3R_TA_CONFIG`) 돌연변이 검사를 추가했다(`mutation_log.md`, 23개 전부 RED).

### 4.2 Q1 — 양자화를 고정하니 기존 패턴이 유지되는가?

**유지되는 정도가 아니라, 값이 하나도 달라지지 않았다.**

- 27모델 × 2 MAC = 54셀의 base 조건에서 **TOTAL과 ACTIVE가 기존 H3와 전부 일치**한다(54/54, `h3_vs_h3r_base.csv`의
  `same_TOTAL_*`·`same_ACTIVE_*` 열). ACTIVE는 1,000 격자 양자화가 없는 지표이므로 이 일치는 격자에 가려진 것이 아니다.
- Vela 스케줄도 같다: OFM block 27/27 일치, ublock 27/27 일치, encoded weight 바이트 54/54 일치, EXT_RD beat 27/27 일치.
- 반면 Vela **산출물 파일의 sha256은 24/27에서 다르다**(6×6 세 모델만 같다 — 그 파생본이 기준과 바이트 동일하므로).
  즉 최종 INT8 양자화 레코드가 달라 컴파일 산출물의 바이트는 달라지지만, 그 차이가 스케줄·전송량·사이클 어디에도 나타나지 않았다.
- 1×1 Conv의 역전도 그대로다: TOTAL 기준 9형상 중 6개에서 512가 느리고(6,068 → 7,068), 9×4·18×2는 동률,
  36×1만 512가 빠르다(10,068 → 7,068). 36×1·12×3 같은 특이 형상의 패턴도 그대로다.
  다만 **9×4·18×2의 "동률"은 TOTAL 격자의 산물**이다 — ACTIVE로 보면 이 두 형상도 512가 0.8% 느리고(5,909 → 5,956),
  아홉 형상 중 여덟에서 512가 0.8–3.7% 느리며 36×1만 빠르다(0.635). 이 구분은 H3에서도 같았다(H13 §6c).

"기존 6개 역전이 그대로 나와야 성공"이라는 게이트는 두지 않았고, 결과적으로 여섯 개가 그대로 나왔다.

**해석의 범위.** 이 결과는 "형상별 calibration 차이가 이 27개 연산의 실행 사이클을 바꾸지 않았다"는 것이다.
양자화 조건이 일반적으로 성능과 무관하다는 뜻이 아니다. 여기서 달랐던 것은 scale·zero-point·bias 값이고,
가중치 **크기**·희소성·연산 구조는 원래 같았다.

### 4.3 Q2 — 같은 모델에서 TA 조건을 바꾸면 무엇이 달라지는가?

base → equalized에서는 크게 달라진다(`base_vs_equalized.csv`).

| 연산 | 256 사이클 변화 | 512 사이클 변화 | r 변화(중앙값) |
|---|---|---|---|
| 1×1 Conv | −1,000 ~ −4,000 | −3,000 ~ −4,000 | 1.165 → 0.754 |
| 3×3 Conv | −4,000 ~ −6,000 | −6,000 ~ −15,000 | 0.936 → 0.561 |
| 3×3 DW | −2,000 ~ −4,000 | −4,000 | 1.000 → 0.674 |

두 MAC 모두 빨라지지만 512가 더 많이 빨라져 r이 내려간다. 1×1 Conv의 역전은 equalized에서 사라지고
(아홉 형상 모두 r < 1), 3×3 Conv의 형상 차이는 거의 사라지며(spread 0.3551 → 0.0493), DW는 반대로 형상 차이가
없던 상태에서 생긴다(0.0000 → 0.4916).

**이 비교는 TA 설정 묶음의 개입 효과다.** equalized는 EXT 읽기·쓰기 지연, EXT_BWCAP, SRAM 읽기·쓰기 지연,
EXT_MAXR, EXT_MAXW를 한꺼번에 바꿨다. 따라서 이 변화를 지연·대역폭·동시성 중 하나만의 효과라고 쓰지 않는다.
어느 성분이 얼마나 기여했는지는 §4.4의 연결 대조군이 **동시성 성분에 한해** 답한다.

### 4.4 Q3 — DW의 기존 relaxed 차이에 MAXR/MAXW 비대칭이 기여했는가?

**기여하지 않았다. 측정 가능한 수준에서 전혀.**

연결 대조군은 두 단계를 분리한다.

| 단계 | 조건 | 결과 |
|---|---|---|
| 기존 H3 DW relaxed | 형상별 양자화 + 기존 relaxed TA | 기준 |
| → bridge_legacy_relaxed | **공통 양자화** + 같은 relaxed TA | 9형상 × 2 MAC 모두 기존 H3 relaxed와 **동일** |
| → equalized | 공통 양자화 + **MAXR/MAXW까지 동일화한 TA** | bridge와 **7개 카운터 전부 동일** (18/18) |

두 번째 행은 양자화만 바꾼 것이고, 세 번째 행은 거기서 EXT_MAXR(256: 24 → 0, 512: 이미 0)과 EXT_MAXW
(256: 12 → 0, 512: 32 → 0)를 추가로 동일화한 것이다. 비교 대상은 TOTAL·ACTIVE·IDLE·SRAM_RD/WR·EXT_RD/WR 일곱 값이며,
**9형상 × 2 MAC = 18개 조합에서 일곱 값이 모두 같았다**(ACTIVE 포함이므로 격자 양자화에 가려진 일치가 아니다).
같은 조합에서 AXF sha는 18/18 모두 다르다 — 서로 다른 TA 설정이 실제로 빌드에 들어갔고, 그런데도 실행이 같았다.

따라서 H13 §6b′가 남겨둔 "relaxed에서도 MAXR/MAXW가 MAC 간 달랐다"는 통제 결함은 **실재했지만 결과를 만들지 않았다**.
DW의 형상별 차이는 비대칭을 제거한 뒤에도 그대로 남는다(spread TOTAL 0.4916, ACTIVE 0.2517).

**그렇다고 "매핑 자체가 원인"으로 확정하지 않는다.** 이번에 제거한 것은 요청 동시성 설정의 MAC 간 비대칭 하나이고,
equalized 조건에서도 두 MAC은 Vela system_config가 다르고(Low vs Mid_512) 산출물·블록·ublock이 다르다.
남은 차이의 원인은 `NOT ESTABLISHED`다.

### 4.5 Q5 — 실제 block 매핑과의 관계

블록 구성은 TA arm과 무관하다(G1: 같은 모델·MAC이면 모든 arm에서 Vela 산출물이 동일). 아래는 base 기준이며
equalized·bridge도 같은 블록을 쓴다.

| H×W | 1×1 block 256 → 512 | 3×3 block 256 → 512 | DW block 256 → 512 | ublock 256 → 512 |
|---|---|---|---|---|
| 1×36 | 1x36x48 → 1x36x64 | 1x36x48 → 1x36x64 | 1x36x48 → 1x36x128 | 1x4x8 → 1x4x16 (DW 1x2x16 → 1x4x16) |
| 2×18 | 2x18x48 → 2x18x64 | 2x18x48 → 2x18x64 | 2x18x48 → 2x18x128 | 2x2x8 → 2x2x16 |
| 3×12 | 3x12x48 → 3x12x64 | 3x12x48 → 3x12x64 | 3x12x112 → 3x12x128 | 1x4x8 → 1x4x16 |
| 4×9 | **4x10**x48 → 4x10x64 | **4x10**x48 → 4x10x64 | **4x10**x96 → 4x10x128 | 2x2x8 → 2x2x16 |
| 6×6 | 6x6x48 → 6x6x64 | 6x6x48 → 6x6x64 | 6x6x112 → 6x6x128 | 2x2x8 → 2x2x16 |
| 9×4 | 9x4x48 → 9x4x64 | 9x4x48 → 9x4x64 | 9x4x112 → 9x4x128 | 1x4x8 → 1x4x16 |
| 12×3 | **12x4**x32 → 12x4x64 | **12x4**x32 → 12x4x64 | **12x4**x64 → 12x4x128 | 1x4x8 → 2x2x16 |
| 18×2 | 18x2x48 → 18x2x64 | 18x2x48 → 18x2x64 | 18x2x112 → 18x2x128 | 2x2x8 → 2x2x16 |
| 36×1 | **20x2**x48 → 36x2x48 | 36x2x**16** → 36x2x48 | 36x2x48 → 36x2x48 | 2x2x8 → 2x2x16 |

- **H·W의 배치가 경계 조건을 바꾼다.** 같은 면적이라도 폭이 블록 폭보다 좁으면 블록이 채워진다: 4×9는 폭 9에
  블록 폭 10, 12×3은 폭 3에 블록 폭 4, 36×1은 폭 1에 블록 폭 2(그리고 1×1의 256에서는 H도 20으로 잘린다)다.
  **256 쪽 사이클이 공통값 위로 올라가는 형상은 언제나 이 세 형상 안에 있다**: 1×1 base 36×1(10,068, 나머지 6,068),
  1×1 equalized 12×3(5,068)·36×1(6,068), 3×3 base 4×9(32,068)·12×3(36,068)·36×1(50,068), 3×3 equalized 같은 세 형상.
  Vela 자신의 추정 사이클도 같은 순서로 움직인다(1×1 256: 공통 4,591 · 4×9 4,679 · 12×3 4,981 · 36×1 5,818).
  역은 성립하지 않는다 — 블록이 맞지 않는 형상이라고 해서 모든 조건에서 손해를 보지는 않는다(1×1 equalized의 4×9는 중앙값과 같다).
- **256 쪽 비용 증가인가, 512 쪽인가.** r이 낮은 형상은 모두 **256이 비싸진** 경우다: 1×1 36×1은 256이 10,068로
  다른 형상(6,068)보다 크고 512는 7,068로 같다. 3×3 36×1도 256이 50,068(다른 형상 31,068)이고 512는 29,068로 같다.
  256의 36×1 블록만 H를 20으로 자르거나(1×1: 20x2x48, 36 mod 20 = 16) 채널 블록이 16으로 작다(3×3: 36x2x16).
  1×1 base의 256 쪽은 그 밖의 여덟 형상에서 ACTIVE가 **5,909로 완전히 같다** — 즉 256은 블록이 맞는 한 형상에 둔감하다.
  반대로 r이 1보다 큰 경우는 512 쪽이 비싸진 것이다(1×1 base 512: 5,956–6,124 ACTIVE).
- **3×3의 형상 차이를 특정 ublock 비효율로 귀속하지 않는다.** 면적 36에서 패딩에 닿는 OFM 위치 비율이 56%(6×6)에서
  100%(1×36·2×18·18×2·36×1)까지 변하므로(§2.2), 3×3의 형상 간 차이에는 블록 경계와 패딩 비중이 함께 들어 있다.
- **H×W ÷ MAC 같은 비율은 이용률이 아니다.** 이 표의 어떤 값도 실측 PE 이용률이 아니다.

DW는 base에서 아홉 형상 모두 r = 1.000이고 블록도 형상에 잘 맞는다. 형상 차이는 equalized·bridge에서만 나타나며,
그때 EXT_RD beat는 형상과 무관하게 256에서 468, 512에서 474로 거의 같다 — 즉 DW의 차이는 전송량 차이로 설명되지 않는다.

## 6. 기존 결론 중 유지·강화·수정·철회

### 유지 (변경 없음)

- **형상 효과 자체.** 같은 면적·같은 연산에서 형상만 바꾸면 r이 바뀐다. base에서 1×1 Conv spread 0.4628,
  3×3 Conv 0.3551 — H3와 같은 값이고 두 지표에서 성립한다.
- **연산 종류 의존.** `TYPE_DEPENDENT`는 base와 equalized 양쪽, TOTAL과 ACTIVE 양쪽에서 성립한다.
- **256→512 역전의 재현.** 1×1 Conv 면적 36의 여섯 형상에서 512가 느리고, TA를 완화하면 사라진다.
- **256 block–형상 불일치가 손실 조건이라는 서술.** 블록 표(§4.5)는 H3의 블록 표와 같다.

### 강화 (근거가 더 좁아짐)

- **H13 §6b′의 첫 번째 한계가 해소됐다.** "형상별 양자화 때문일 수 있다"는 유보는 이제 필요 없다.
  최종 INT8 가중치·bias·양자화 레코드를 형상 간에 **바이트 단위로 동일**하게 만든 조건에서 같은 값이 나왔다
  (54/54, TOTAL·ACTIVE 모두). 형상 효과는 "형상만 바꾼" 개입의 결과라고 말할 수 있다.
- **H13 §6b′의 두 번째 한계도 해소됐고, 결과는 바뀌지 않았다.** MAXR/MAXW를 MAC 간 동일하게 맞춰도 DW의
  형상별 차이는 그대로다(bridge ↔ equalized 7개 카운터 18/18 동일).
- **지표 의존 1건이 재현됐다.** `MEMORY_SHAPE_INTERACTION:conv1x1`의 TOTAL·ACTIVE 불일치는 우연이 아니다.

### 수정

- **"DW의 형상 효과는 메모리 조건이 아니라 매핑 자체에서 온다"(H13 §6b)는 표현을 쓰지 않는다.**
  DW의 형상 효과는 base에서는 없고(spread 0.0000) 완화된 TA에서만 나타난다(0.4916). 즉 형상 차이가 드러나려면
  메모리 서비스 조건의 완화가 **필요**했다. 동시에 그 완화 안에서 요청 동시성의 MAC 간 비대칭을 제거해도 차이는
  줄지 않는다. 가능한 문장은 이것이다 — 시험한 조건에서 DW의 형상별 차이는 TA 완화가 있어야 나타나고,
  요청 동시성 설정의 MAC 간 비대칭으로는 설명되지 않는다.
- **§4.3의 base↔equalized 차이를 "지연 효과"로 부르지 않는다.** 여러 값을 함께 바꾼 묶음의 효과다.

### 철회

- **철회할 결론은 없다.** H3의 어떤 수치도 이번 통제에서 달라지지 않았다.
  H13 §6b′가 "순수한 형상 개입으로 확정하지 않는다"고 달아둔 **유보**를 철회한다(§4.2).

### 두 통제 문제를 제거한 뒤 무엇이 남고 무엇이 사라졌는가

**사라진 것: 두 개의 대안 설명뿐이다. 측정값은 하나도 사라지지 않았다.**
형상별 양자화 차이로 형상 효과를 설명할 수 없고(모든 값이 동일), 요청 동시성의 MAC 간 비대칭으로 DW의 완화 조건
차이를 설명할 수 없다(모든 카운터가 동일).

**남은 것:** 형상 효과(1×1·3×3 base, 1×1 equalized, DW equalized·bridge), 연산 종류 의존, 256→512 역전,
그리고 이들과 Vela 블록 구성의 대응. 남은 미해결은 다음과 같다.

- equalized에서도 두 MAC은 Vela system_config·산출물·블록이 다르므로 "물리 MAC 배열 크기만의 효과"는 여전히 측정되지 않았다.
- 3×3의 형상 차이에서 블록 경계 성분과 패딩 비중 성분(56%–100%)을 분리하지 못했다.
- DW가 왜 완화된 TA에서만 형상 차이를 드러내는지의 메커니즘은 `NOT ESTABLISHED`다.
- TOTAL 1,000 격자는 이 규모(2,000–6,000 사이클)에서 값의 16–50%이므로, 소형 연산의 정밀 비교는 여전히 제약된다.
- 면적 64·256과 MAC 1024·2048은 이번 범위가 아니다. 그 범위의 기존 결론이 H3-R로 검증됐다고 서술하지 않는다.
