## 2. H1-B — 요청 동시성 EXT_MAXR (RNNoise U85 256·512)

s(M) = [C(R=1000) − C(R=250)] / 750, 쓰기 지연은 프로파일 기본:

| MAXR | 256: C(250) / C(1000) / s | 512: C(250) / C(1000) / s |
|---|---|---|
| 1 | 243,086 / 951,086 / 944 | 247,086 / 969,086 / 963 |
| 4 | 68,086 / 250,086 / 243 | 70,086 / 254,086 / 245 |
| 16 | 36,086 / 113,086 / 103 | 34,086 / 106,086 / 96 |
| 63 | 36,086 / 113,086 / 103 | 32,086 / 99,086 / 89 |
| 64 | 36,086 / 113,086 / 103 | 32,086 / 99,086 / 89 |
| 0 (무제한) | 36,086 / 113,086 / 103 | 32,086 / 99,086 / 89 |

판정: 두 MAC 모두 `CONCURRENCY_REDUCES_SENSITIVITY`. 64 = 0과 동일 → `MAXR64_IS_UNLIMITED`. 근거는 측정 일치만이
아니라 드라이버 소스다: `dependencies/core-platform/drivers/timing_adapter/src/timing_adapter.c`의
`TA_MAXR_MASK 0x0000003F`와 `ta_set_maxr(): reg = val & TA_MAXR_MASK` — 64 & 0x3F = 0, 즉 레지스터에는 0(무제한)이
쓰인다. 따라서 MLEK mid·high 프로파일의 `EXT_MAXR=64`는 실제로 무제한이며, 이 캠페인과 X4·동결 측정의 512·1024·2048
셀은 모두 그 조건에서 측정된 것이다(설정값 ≠ 적용값의 실례, 생성 헤더에는 64로 남는다). 256의 프로파일 기본 24는
16·63·0과 같은 값을 내므로 이 산출물은 16 이상에서 동시성이 포화한다.

**답할 것.** 바꾼 것: TA가 허용하는 미완료 읽기 요청 수(EXT_MAXR). 달라진 것: 읽기 지연 250→1000 구간의 평균 민감도가
MAXR 1 → 4 → 16에서 약 9.4 → 2.4 → 1배로 줄고 그 위는 변화 없음. EXT_MAXR=1로 읽기 요청 동시성을 제한한 조건에서 이
구간 평균 민감도는 설정 지연 1사이클당 PMU 944/963사이클이었다(256/512 MAC). 이는 구간 평균 민감도이지 전체 NPU의 직렬
실행, 일정한 전 구간 기울기, 왕복 횟수를 뜻하지 않는다. 좁힌 것: RNNoise의 지연 민감도(≈90–100)는 "요청을 병렬로 낼
수 있어도 남는 부분"이다.

256은 절반으로 줄이면 9% 느려지고 올려도 빨라지지 않는다. 지연 제거는 512에서 7.8%, 256에서 1.3%만 줄인다. 예측 대조:
H2′-a("잔여 비용에 외부 대역폭 제약이 기여")는 512에서 지지되지 않고 256에서도 기본 cap이 제한하고 있다는 근거는 없다.
좁힌 것: Wav2Letter에서 cap 완화·지연 제거에 따른 개선은 사전 임계값(10%) 미만이다(512: 지연 제거 7.8%, cap 완화 0%;
256: 1.3% / 0.6%). 잔여 비용의 후보에서 "시험 범위의 외부 대역폭 상한"은 512에서 빠지고, SRAM 경로·계산·내부 처리가 남는다
(GO §4 분기표 3행). H2-B 진행 조건(`EXT_CAP_CONSTRAINED`)은 두 셀 모두 미충족 → 원 H2-B `NOT_TRIGGERED`, 탐색 확장 H2-B-X는
계획서 A4.

### 5c. A3 — 지연 0/0에서 MAXR (서술)
