## 2. H1-B — 요청 동시성 EXT_MAXR (RNNoise U85 256·512)

s(M) = [C(R=1000) − C(R=250)] / 750, 쓰기 지연은 프로파일 기본:

| MAXR | 256: C(250) / C(1000) / s | 512: C(250) / C(1000) / s |
|---|---|---|
| 1 | 243,086 / 951,086 / 944 | 247,086 / 969,086 / 963 |
| 4 | 68,086 / 250,086 / 243 | 70,086 / 254,086 / 245 |
| 16 | 36,086 / 113,086 / 103 | 34,086 / 106,086 / 96 |
| 63 | 36,086 / 113,086 / 103 | 32,086 / 99,086 / 89 |
| 64 | 36,086 / 113,086 / 103 | 32,086 / 99,086 / 89 |
| 0 (무제한) | 36,086 / 113,086 / 103 | 32,086 / 99,086 / 89 |

판정: 두 MAC 모두 `CONCURRENCY_REDUCES_SENSITIVITY`. 64 = 0과 동일 → `MAXR64_IS_UNLIMITED`. 근거는 측정 일치만이
아니라 드라이버 소스다: `dependencies/core-platform/drivers/timing_adapter/src/timing_adapter.c`의
`TA_MAXR_MASK 0x0000003F`와 `ta_set_maxr(): reg = val & TA_MAXR_MASK` — 64 & 0x3F = 0, 즉 레지스터에는 0(무제한)이
쓰인다. 따라서 MLEK mid·high 프로파일의 `EXT_MAXR=64`는 실제로 무제한이며, 이 캠페인과 X4·동결 측정의 512·1024·2048
셀은 모두 그 조건에서 측정된 것이다(설정값 ≠ 적용값의 실례, 생성 헤더에는 64로 남는다). 256의 프로파일 기본 24는
16·63·0과 같은 값을 내므로 이 산출물은 16 이상에서 동시성이 포화한다.

**답할 것.** 바꾼 것: TA가 허용하는 미완료 읽기 요청 수(EXT_MAXR). 달라진 것: 읽기 지연 250→1000 구간의 평균 민감도가
MAXR 1 → 4 → 16에서 약 9.4 → 2.4 → 1배로 줄고 그 위는 변화 없음. EXT_MAXR=1로 읽기 요청 동시성을 제한한 조건에서 이
구간 평균 민감도는 설정 지연 1사이클당 PMU 944/963사이클이었다(256/512 MAC). 이는 구간 평균 민감도이지 전체 NPU의 직렬
실행, 일정한 전 구간 기울기, 왕복 횟수를 뜻하지 않는다. 좁힌 것: RNNoise의 지연 민감도(≈90–100)는 "요청을 병렬로 낼
수 있어도 남는 부분"이다.

H2′-a("잔여 비용에 외부 대역폭 제약이 기여")는 512에서 지지되지 않고 256에서도 기본 cap이 제한하고 있다는 근거는 없다.
좁힌 것: Wav2Letter에서 cap 완화·지연 제거에 따른 개선은 사전 임계값(10%) 미만이다(512: 지연 제거 7.8%, cap 완화 0%;
256: 1.3% / 0.6%). 잔여 비용의 후보에서 "시험 범위의 외부 대역폭 상한"은 512에서 빠지고, SRAM 경로·계산·내부 처리가 남는다
(GO §4 분기표 3행). H2-B 진행 조건(`EXT_CAP_CONSTRAINED`)은 두 셀 모두 미충족 → 원 H2-B `NOT_TRIGGERED`, 탐색 확장 H2-B-X는
계획서 A4.

### 6b. 답할 것

**바꾼 것.** 원소 수·채널·가중치·연산 종류를 고정하고 H×W 형상만; 면적을 36 → 64 → 256; 연산 종류; TA 조건.

**달라진 것.**
- 면적 36 1×1 Conv: 9개 형상 중 6개에서 512가 256보다 **느리다**(6,068 → 7,068, r 1.165). 9×4·18×2는 동률, 36×1만 512가
  빠르다(10,068 → 7,068). 즉 RNNoise에서 본 256→512 역전이 합성 단일 연산에서 재현된다. TA를 완화하면 아홉 형상 모두
  512가 빠르다(r 0.75, 36×1은 0.67). 역전은 MAC 프로파일 전환에 딸린 메모리 서비스 조건(512의 지연이 2배)에서만 나타난다.
- 이 모델들의 절대 사이클은 6,068 / 7,068 / 4,068 / 3,068처럼 1,000 격자 위에 있고 연산량과 거의 무관하다(1×1 Conv 면적 36의
  MAC 수 589,824는 256 MAC/cycle로 2,304사이클이지만 실측은 6,068). 이 크기의 연산에서 TOTAL은 계산이 아니라 명령·데이터
  이동의 고정적 순서(왕복 몇 번)로 정해진다. 그 격자의 기원은 A5 진단(§5d)에서 다룬다.
- 3×3 Conv: 면적 36에서는 r 0.936(512가 6% 빠름)이고 36×1·12×3·4×9 같은 좁은 형상에서만 r이 크게 낮다(0.58–0.91) — 256 MAC의
  block이 형상에 맞지 않아(36×1은 OFM block 36x2x16, ublock 2×2×8로 너비 1을 2로 채움) 256 쪽이 손해를 보는 경우다. 면적이
  커지면 r이 0.67(64) → 0.45–0.56(256)으로 떨어져 512의 이득이 나타난다. TA 완화에서는 면적 36 모든 형상이 r ≈ 0.56.
- 3×3 DW: 면적 36·64에서 512는 256과 **같거나 느리다**(r 1.0, 4×16·8×8은 1.11). 면적 256에서만 0.77–0.87. TA 완화에서는
  면적 36 r 0.67(18×2만 1.0, 36×1은 0.51).

**예측 대조.** H3′("작은 공간 크기와 출력 형상의 블록 매핑 특성이 특정 MAC 전이의 비용 변화와 연관")은 통제 개입에서
지지된다: 같은 면적에서 형상만 바꿔도 r이 바뀐다(`SHAPE_EFFECT`), 연산 종류에 따라 다르다(`TYPE_DEPENDENT`). 단
"작은 면적 자체가 원인"은 conv3x3에서만 성립하고(`AREA_EFFECT`), conv1x1·dw3x3에서는 면적을 키워도 단조롭게 좋아지지
않는다. 그리고 conv의 형상 효과는 TA를 완화하면 대부분 사라진다(`MEMORY_SHAPE_INTERACTION`) — 형상 효과의 큰 부분은
메모리 서비스 조건(프로파일 전환)과 결합된 것이다. dw3x3는 반대로 완화에서 형상 차이가 커지므로, DW의 형상 효과는
메모리 조건이 아니라 매핑 자체에서 온다.

**좁힌 것.** 요인 5("작은 feature map")는 "면적"이 아니라 "형상 × 연산 종류 × 메모리 서비스 조건"의 결합으로 좁혀진다.
요인 7("ublock 형상 변화")은 ublock 전환 자체가 아니라 256 쪽 block이 좁은 형상(36×1, 12×3)에 맞지 않는 경우에 r이 낮아지는
것으로 구체화된다(표의 block 열). 요인 4(DWConv)는 합성 모델에서 "DW는 256→512에서 이득이 없거나 손해"로 확인되지만, 실제
모델(A6)에서 DW가 Conv보다 나쁘지 않았던 것과 함께 읽으면 모델 수준의 DW 비중은 예측 변수가 아니고 개별 DW 연산의 면적이
문제다. 요인 6(연산량 하한)은 "면적 36 연산은 종류·형상과 무관하게 ≈6,000 사이클"로 정량화된다.

## 7. S4 — H2-B `NOT_TRIGGERED` · H2-B-X 탐색 대조 (계획서 A4, 6 arm, 판정값 없음)

대표 레이어: Wav2Letter op 15 (7-tap 250→250 Conv2D, 가중치 437,500 B, 원본 flatbuffer에서 그대로 절단, 원본 실행의
IFM→OFM 재생이 바이트 동일). Vela 스케줄은 세 배치에서 동일(OFM block [1,1,84,48], IFM block [1,1,92,16], ublock [1,4,16],
PartKernel; 512 MAC). 인코딩 가중치 275,344 B(Shared) vs 276,240 B(Sram_Only·Dedicated). 세 배치 모두 출력 바이트 동일.

| 512 | Shared_Sram | EXT → SRAM staging / SRAM | 149,068 | 17,260 / 0 | 61,820 / 21,586 | — |

Dedicated_Sram 512의 EXT beat(56,343 / 4,377)는 Sram_Only 512의 SRAM beat와 정확히 같다 — 같은 전송을 다른 메모리로 보낸
순수 배치 교체다. Shared_Sram은 가중치를 EXT에서 한 번 읽어(17,260 beat ≈ 276 KB / 16 B) SRAM으로 옮기는 단계가 SRAM 쓰기
+17,200 beat로 보인다. 256의 Dedicated는 IFM block 재사용이 달라 EXT 읽기가 77,830으로 늘고 SRAM cache(34,510 / 17,255)를
쓰는데, 지연 250/125 프로파일에서 +77%가 된다.

**서술.** 이 레이어에서 가중치를 SRAM에 두면 Shared 대비 512에서 10%, 256에서 5% 빨라지고, 모든 텐서를 DRAM에 두면 512에서
12%, 256에서 77% 느려진다. 이는 대표 레이어 한 개에 한정된 관측이며 H2′의 검증 성공으로 합치지 않는다(원 H2-B는
`NOT_TRIGGERED`). 16 MB·4 MB 레이어로 일반화하지 않는다. 다만 "BWCAP 완화 효과가 작다"(§5a)가 "배치 효과가 없다"를 뜻하지
않는다는 매니저의 지적이 이 대조로 확인된다: 대역폭 상한을 풀어도 줄지 않던 비용이 배치를 바꾸면 줄어든다.
