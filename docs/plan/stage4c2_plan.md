# Stage 4C-2 계획 — 입력 채널 수에 따른 1×1 Conv의 MAC 처리율 (2026-11-11)

Owner 지시(2026-11-11)를 요약한 계획. 계약은 `evidence/stage4c2/contract.md`이다. **TA profile 1.**

## 질문

같은 1×1 Conv(24×24, Cout 96, VALID, RELU6)에서 Cin을 16 → 32 → 64 → 128로 늘릴 때 다음을 본다.
- MAC_ACTIVE가 계산량에 비례해 늘어나는가, 아니면 활성 사이클당 유효 처리량이 좋아지는가?
- 그 변화가 block·ublock·처리 순서와 어떻게 함께 나타나는가?

메모리 쓰기 규칙 확장, DW 커널 변경, FC, 공간 크기, 배치·TA 변경은 범위 밖이다.

## 설계

- **데이터:** Stage 4 Conv 기준의 IFM·가중치를 고정 seed(20261111)로 128채널까지 한 번 확장하고, 앞 Cin개를 쓴다.
  - 앞 16채널은 기준과 같고, 구성 사이 공통 채널도 같다(컨테이너에서 확인).
  - bias와 OFM scale은 기준 값이며 재보정하지 않는다. 포화는 기록만 한다.
- **Cin 16:** 기존 기준 DRWL(`2681c566`)을 그대로 쓴다. 다시 만든 Cin 16 모델은 이름 문자열만 다르고 command stream이 같다.
- **컴파일 결과(Gate B 4/4):**
  - 공통: OFM block 6×12×96, ublock 2×2×32, kernel 2개(출력 채널 16+80), 각 kernel이 IFM 전체 깊이 처리, 누산 RESET
  - Cin 16·32: PartKernel, IFM block 6×12×16
  - Cin 64·128: DepthFirst, IFM block 6×12×64
  - 그래서 16→32, 64→128은 같은 스케줄 안의 입력 채널 효과이고, 32→64는 스케줄 변화가 섞인 종합 효과다.
- **정규화:** 출력 ublock 수(576, 네 구성 동일)와 입력 방향 단계 수(1·2·1·2)를 산출물에서 계산한다.
  - MAC_ACTIVE ÷ ublock 수는 전체 측정값을 정규화한 값이지, ublock 하나의 시간이 아니다.
- **사전 예측식:** 두지 않는다. 기존 자료가 Cin 15·16뿐이라 Cin 의존성을 도출할 근거가 없다.
